# 全局工程规范

本文件是本仓库所有开发、修复、重构和评审工作的统一约束。产品与技术 Spec 统一维护在 `.ai/specs/`；需要澄清的产品决策由开发者在当前协作中确认。

## Spec 文档

- 每个已确认的重要产品能力、架构演进或跨模块改造都可以在 `.ai/specs/` 创建一个 Markdown Spec；文件名使用小写英文、数字和连字符，例如 `bookstore-2.0-spec.md`。
- Spec 是需求目标、范围、领域规则、接口/数据契约、验收标准和待确认决策的权威来源；代码改动影响这些事实时，必须同步更新相关 Spec。
- Spec 以决策和可验证结果为中心，不维护 Task、Verify、Review、索引或需求工作目录等流程文档；开发进度仍在当前协作与代码提交中沟通。
- 除非开发者明确要求修改规范，否则 `.ai/rules/` 为只读；`.ai/specs/` 可在当前任务范围内创建和更新。

## 变更边界

- 先理解相关代码、调用方、测试和仓库既有约定；禁止基于未验证的假设改变产品行为、公共接口、数据格式或架构边界。
- 仅做解决当前目标所需的最小改动。不得混入无关重构、依赖升级、批量格式化或删除用户未授权内容。
- 新增代码前先搜索已有实现；遵循“复用 > 扩展 > 新建”。
- 发现范围外问题时如实报告，不擅自扩大实现范围。
- 保留并避开工作区中与当前目标无关的未提交改动；不得使用会覆盖或重置用户工作的操作。

## 设计与代码质量

- 保持单一职责、清晰命名和稳定的模块边界；代码应让维护者无需依赖隐含上下文即可理解。
- 功能变更与行为保持型重构分开实施和验证。重构前先建立现有行为的安全网，重构不得改变可观察行为。
- 公共 API、异常语义、序列化格式、数据库契约和配置项的变更，必须检查调用方、兼容性影响与相关文档。
- 捕获异常仅在能够恢复或补充上下文的位置进行；不得吞掉异常，并应保留原始原因。
- 注释说明原因、约束、权衡或非显然风险；禁止用注释逐行复述代码，且代码变化时同步更新相关文档。

## 数据与安全

- 所有外部输入、请求参数、文件内容、消息和第三方响应默认不可信；在信任边界执行格式、范围和业务校验。
- 涉及权限时在服务端执行授权校验，遵循最小权限原则；禁止仅依赖前端限制。
- 不在源码、日志、测试样例或文档中提交密钥、令牌、密码、个人数据或其他敏感信息。
- 数据写入、迁移、删除和批量更新必须明确影响范围、失败处理、幂等性或回滚策略（适用时）。

## 验证与交付

- 每次变更后按风险获取证据：优先运行格式化、编译/类型检查和最小相关测试；涉及模块协作、核心路径、数据、安全或并发时扩大到集成、端到端或专项验证。
- 测试从调用者视角覆盖核心行为，并补充分支、边界、异常、状态副作用和资源清理。测试必须有有效断言，避免真实网络、固定延迟、执行顺序依赖和不可控时间。
- 性能结论必须有可复现的基准或测量；安全结论必须有明确的信任边界和数据流证据。未执行的检查不得表述为已通过。
- 交付时说明完成内容、实际运行的验证及结果；对未验证项说明原因、替代证据和剩余风险。

## 协作与提交

- 一个提交只表达一个完整、可验证的意图；提交前检查 diff，确保没有调试输出、临时开关、死代码、无关文件或未经处理的警告。
- 提交信息使用清晰的动词短语，描述“做了什么”，必要时补充“为什么”；不将多个独立变更混在同一提交中。
- 评审意见必须给出具体位置、触发条件、用户影响、证据和可行的最小修复方向；将缺陷、明确约定偏差与个人偏好区分开。
