# 旧工作流迁移

## 安全原则

保留旧 YAML、旧 **.ai/work/**、1.0.0 的 **.ai-dev/requirements/** 和 1.0.1 的 **.ai/requirements/**，默认迁移到 **.ai/<需求名称>/<Spec 语义目录>/**。禁止静默删除、覆盖或归档原文件；只有开发者明确确认后才可归档。V2 新写入只生成 Markdown，不长期维护两套事实源。

## 迁移步骤

1. 清点 **tasks.yaml**、**index.yaml**、**Txxx.yaml**、**.ai/work/**、**.ai-dev/requirements/**、**.ai/requirements/** 及其关联文件，记录来源路径。
2. 确认每项所属 Requirement 和 Spec；旧 Plan 仅作为迁移输入提取 Task、依赖、风险与评审信息，不在新结构中重建；无法确定归属或发现重复 ID 时停止对应项并报告。
3. 映射 Task ID、标题、状态、优先级、依赖、描述、验收标准、执行记录、Finding 和 Verify/Review 关联。
4. 不得编造业务内容；缺失字段统一写“待确认”，并让状态保持在不可误判完成的位置。
5. 在 **.ai/<需求名称>/<Spec 语义目录>/** 生成 Markdown；目录名根据业务语义动态生成，不机械复制 ID。保留来源路径与旧 ID，原文件保持不变。
6. 按 **.ai/rules/indexes.md** 执行一致性检查，成功后再重建索引。
7. 输出迁移报告：成功项、跳过项、失败原因、待确认字段、生成路径和仍保留的旧文件。

## 迁移状态映射

仅在语义明确时映射到 V2 固定状态。旧状态无法无歧义对应时标记“待确认”，禁止猜成 DONE、PASS 或已评审。旧 Verify/Review 证据若缺少范围、版本或验收关联，作为历史备注保留，不视为当前有效门禁。
